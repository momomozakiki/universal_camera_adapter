### [fix] example/lib/ezviz/ezviz_camera_adapter.dart, example/lib/camera_session.dart, lib/src/persistence/ — a saved EZVIZ camera made the app impossible to launch

- **Symptom:** After installing `1.0.2+3` on `CPH2113` (Android 12) the app died on every launch
  with `FATAL EXCEPTION: DefaultDispatcher-worker-N` /
  `java.lang.NullPointerException: … EZGlobalSDK.getDeviceList(int, int) on a null object reference`
  at `EzvizManager.kt:333`. The crash happens during startup restore, **before any UI exists**, so
  there was no screen from which to remove the camera causing it — recoverable only by wiping app
  data or editing preferences over `adb`.
- **Root cause (ours, latent — NOT a regression):** `EzvizCameraAdapter.listDevices()` called the
  native `getDeviceList` with no prior `initSDK`; init only ever happened inside `open()`. Restoring
  a saved EZVIZ camera *enumerates before it opens*, so `EZGlobalSDK.getInstance()` was null.
  `git log -L 40,45:…/ezviz_camera_adapter.dart` dates this to `8d10645` (2026-07-22).
- **Why it only surfaced now:** no saved profile was marked default, so
  `CameraSession._defaultProfile()` fell back to "most recently created wins". Adding an EZVIZ
  camera at 05:13 silently promoted it into the startup path. The trigger was *saved data*, not the
  APK.
- **Why no Dart `try`/`catch` helped:** the vendored plugin's `getDeviceList` catches only
  `BaseException` (the EZVIZ SDK's own type), so a `NullPointerException` escapes the coroutine and
  kills the process. (An earlier reading of this file mistook the adjacent voice-talk function's
  `catch (e: Exception)` for this one — the file mixes both, 12 `BaseException` vs 8 `Exception`.)
- **What changed:**
  1. `_ensureSdk()` extracted in `EzvizCameraAdapter` — token fetch + `initSDK` — now called by
     **both** `listDevices()` and `open()`. `listDevices` also gained the exception ladder used by
     `FlutterCameraAdapter.listDevices` (`TimeoutException` rethrown, `on Object` → authored
     `StateError`), since this backend had no error mapping at all and would have leaked a raw
     `PlatformException` across the adapter boundary.
  2. New `CameraRestoreGuard` + `SharedPreferencesCameraRestoreGuard` (`lib/src/persistence/`),
     injected into `CameraSession`. Marks before the risky open, clears after; a launch finding the
     mark still set skips the auto-open and lands on the Cameras tab with
     `kRestoreSkippedAfterCrash`. Backend-agnostic — the only defence available when a backend kills
     the process rather than throwing. `endRestore()` is in a `finally` so a *Dart* failure never
     suppresses the next launch.
  3. `_defaultProfile()` no longer falls back to most-recent-wins; and
     `SharedPreferencesCameraProfileStore.save()` marks the first profile in an **empty** store as
     default (scoped to empty deliberately — "promote when nothing is default" would re-create the
     old behaviour on existing installs).
  4. Defensive null check on `EZGlobalSDK.getInstance()` in the vendored `EzvizManager.kt`
     `getDeviceList`, returning `SDK_NOT_INITIALIZED` instead of dying. ~20 sibling call sites in
     that file share the same unguarded shape; only the one on the startup path was fixed.
- **Verified:**
  - **A/B on hardware, before writing any code:** the old `1.0.1+2` — which *is* the parent commit
    `0aaf469`, whose commit message bumped that version — was launched against the same app data and
    crashed with the byte-identical NPE, `pidof` empty. This empirically exonerated `36f6e06` and
    satisfied the Android handoff's "confirm it IS this commit" gate.
  - `1.0.3+4` installed with `adb install -r -d` (**data preserved** — all four saved cameras and the
    ONVIF password kept; no `pm clear`, no prefs surgery needed for recovery). Cold launch: process
    alive, zero `AndroidRuntime` output, lands on the Cameras tab with all four cameras listed, none
    auto-opened, and no retro-promotion of a default (all four still `isDefault:false`).
  - **The exact killing scenario re-run:** EZVIZ set as default via a backed-up `run-as sed` edit,
    then launched. App alive, no fatal exception, `Default` chip rendered on the EZVIZ card, and the
    `uca.restore_in_progress` flag observed **set during** restore and **cleared after** — the guard
    lifecycle confirmed on real hardware. Device state reverted to as-found afterwards.
  - Gates (all via PowerShell — the `flutter` shim under Git Bash on this machine exits 0 without
    running anything): `flutter analyze --fatal-infos` clean; root `flutter test` **153** (was 146);
    `example/` **112** (was 106); hook tests **33**.
  - Two pre-existing tests failed legitimately against the new rules and were corrected, not
    silenced: the store round-trip test (first save now sets `isDefault`) and an `updateProfile` test
    that had relied on most-recent-wins to open an unflagged profile.
- **Candidate A (from the Android handoff) — separately confirmed, deliberately NOT fixed:** new
  `test/flutter_camera_adapter_error_test.dart` drives a camerax-shaped `PlatformException`
  (`code: 'ExecutionException'`, message containing `InitializationException`) through the real
  `FlutterCameraAdapter.listDevices()` via a mock method channel — no new dependency needed. It
  records that a permission denial wrapped in an `InitializationException` currently classifies as
  "no camera" and returns an empty list. Written as characterisation, not endorsement: narrowing
  `meansNoCamera()` trades directly against the stack trace `36f6e06` removed, and needs a real
  logcat payload from an affected device to narrow *against*. Not observed on `CPH2113`, whose
  built-in cameras enumerate and preview normally (zoom 1.0×–10.0× confirmed on the PTZ tab).
- **Closes the "is that possible caused by the Windows fix" question:** no. The only unplanned
  Windows change in this history is a single UTF-8 BOM byte on `scripts/build-apk.ps1` in `0aaf469`;
  `1.0.2+3` was built *by* that script, and the parallel Windows session changed no code at all.

### [fix] example/lib/tabs/cameras_tab.dart, example/lib/ezviz/ezviz_camera_adapter.dart — actual root cause of the persisting Android rename crash found and fixed

- **What:** The `_dependents.isEmpty` red-screen crash on renaming a saved camera (Android,
  built-in backend) persisted through two prior fix attempts (`9154be7`, `4382db7`), both of
  which targeted camera-preview widget mounting/re-opening. Investigated on a dedicated branch
  (`fix/camera-rename-dependents-crash`, cut from `main`) specifically so `main` stayed untouched
  until the real cause was confirmed. Root-caused by running the example app via `flutter run`
  directly on the connected Android device (`CPH2113`) and reading the Dart tool's own stdout
  rather than `adb logcat` — the prior attempts' logcat was rate-limited and never captured the
  actual assertion stack; this time it did. The captured trace's exception header reads exactly:
  **"A TextEditingController was used after being disposed"**, naming `TextField` at
  `cameras_tab.dart:88:18` — the rename dialog's own text field, nothing to do with any camera
  preview. `_renameCamera`'s old code called `controller.dispose()` immediately after
  `Navigator.pop`'s `showDialog` future resolved, racing the `AlertDialog` route's still-in-flight
  exit transition, which was still rebuilding that `TextField`'s subtree for one more frame — the
  disposed-controller access there cascades into the `_dependents.isEmpty` framework assertion as
  a secondary failure in the same frame. Fixed by extracting a `_RenameDialog extends
  StatefulWidget` that creates its own `TextEditingController` in a field initializer and disposes
  it in its own `dispose()`, tying the controller's lifetime to the dialog element's own teardown
  instead of racing it from the caller.
- **Also fixed (separate, unrelated parity gap found during the same investigation):**
  `example/lib/ezviz/ezviz_camera_adapter.dart`'s `buildPreview()` was the only preview builder not
  wrapped in `KeyedSubtree(key: ValueKey(...))`, unlike the built-in (`flutter_camera_adapter.dart`)
  and ONVIF (`rtsp_preview.dart`) adapters, both patched by `9154be7`. Wrapped in
  `KeyedSubtree(key: ValueKey(device.id), ...)` for the same defense-in-depth (forces a clean
  remount instead of reusing a platform view across a re-open onto a different device). Not related
  to the rename-crash root cause — EZVIZ was never the active backend in the confirmed repro — but
  the same class of hazard the other two adapters were already patched against.
- **Why:** Two prior fixes had each targeted camera-preview mounting (multi-tab platform-view
  reuse, controller re-open on rename) and each admitted, in their own commit bodies, that the fix
  was never verified against a captured on-device stack trace. The crash kept recurring because
  neither fix addressed the actual mechanism — `CamerasTab` (where the crash reproduces) renders no
  camera preview at all, so neither prior theory could have been correct for this repro path.
- **Verified:**
  - Reproduced live on hardware (`CPH2113`, debug build) with the real stack trace captured via
    `flutter run` stdout before any fix was written.
  - Fix confirmed on the same hardware: user renamed the same camera 3 times in a row with no crash
    (debug mode).
  - New regression test `example/test/cameras_tab_rename_test.dart` drives the actual `showDialog` →
    type → Save flow and steps through the dialog's exit-transition frames explicitly (rather than
    jumping straight to `pumpAndSettle()`, which would skip past the vulnerable frames and could
    pass even on the buggy code), asserting no exception after each step. Confirmed red-then-green:
    stashed the fix and re-ran the test — it failed with the exact same "TextEditingController was
    used after being disposed" / cascading `_dependents.isEmpty` trace captured on the real device;
    restored the fix and it passed.
  - Full suite green after the fix: `flutter analyze --fatal-infos` clean at repo root and in
    `example/`; `flutter test` — 130 tests at repo root (includes `example/`'s 27 in that run),
    all passing.
  - Audited the other two `TextEditingController` sites in the app (`example/lib/setup/
    onvif_setup_wizard.dart`, `example/lib/ezviz/ezviz_wizard_flow.dart`) — both already own their
    controllers as `State` fields disposed in their own `dispose()`, the safe pattern; no changes
    needed there.
  - Release-mode (`flutter run --release`) verification was attempted but the Gradle build daemon
    crashed (JVM crash, ~10 minutes in) — an environment/infra issue on this machine unrelated to
    the code change, not a sign of a regression. User opted to accept the debug-mode confirmation
    (3× manual + passing regression test) rather than retry, given the root cause is a genuine
    object-lifecycle bug, not debug-assertion-only behavior.
- **Discovered, not acted on this round (explicit scope decision):** `9154be7`/`4382db7` — the two
  prior fix attempts named above — are **not ancestors of `main`**; they exist only on the separate,
  unmerged `feat/workflow-branch-discipline` branch. This branch was cut from `main`, so `main`

### [code] lib/src/plugin_error_mapping.dart, lib/src/flutter_camera_adapter.dart, example/lib/** — stop leaking raw platform exceptions to the UI, and make the tri-state feature model visible

- **What:** Two defects behind one screenshot (a full CameraX Java stack trace filling the "Built-in
  camera" wizard). (1) `camera_android_camerax` 0.7.4+1's `availableCameras()` has **no `try`/`catch`
  at all** (`android_camera_camerax.dart:291-331`), so a CameraX failure arrives as a bare
  `PlatformException`; our only guard caught `CameraException`, a different type. New
  `lib/src/plugin_error_mapping.dart` classifies and wraps it: the device-reports-no-camera case
  returns an **empty list**, everything else a `StateError` with a written message. (2) The wizard
  ended in `on Object catch (e) { _fail('$e'); }` — five other sites did the same. New
  `example/lib/error_messages.dart` is now the single error→sentence translation point, and
  `CameraEmptyState` renders a friendly "No built-in camera found" with a cause-specific hint.
  Separately, the tri-state `CameraFeatureStatus` model existed but was invisible: every consumer
  went through `CameraSession.supports()` → `isSupported()`, which returns `false` for `unvalidated`,
  so "wired but unproven" and "hardware cannot" read identically. Added `CameraSession.statusOf`,
  `FeatureStatusChip`, a Features tab, and flipped the base `featureMatrix` derivation from
  optimistic (`frameCapture`/scanning defaulted to `supported`) to fail-safe, with a new
  `CameraAdapter.declaredFeatures` as the one place a backend states a claim.
- **Why:** The contract at `camera_adapter.dart:24-27` promises failures "never" surface as a raw
  platform exception; on Android that was simply untrue. The Pigeon `wrapError` shape
  (`CameraXLibrary.g.kt:29-38`) is what made it so damaging — `message` is `exception.toString()` and
  `details` carries the `at androidx.…` frames, and `PlatformException.toString()` prints all three.
  That is also why the mapping never reads `message` for display, only for classification. The
  feature-default flip closes the matching trap on the feature side: opt-out defaults meant a backend
  that merely *forgot* inherited a claim its hardware could not honour, and the user was told the
  *camera* lacked something the *app* had not wired (EZVIZ's `unvalidated` frame capture, live today).
- **Verified:** `flutter analyze --fatal-infos` clean; `flutter test` 146 passing (root) and 101
  (example); `python -m unittest discover -s tests/hook` 33 passing. Permission detection was switched
  from substring matching to the exact platform code after confirming from source that **both**
  platforms emit the same constant (`CameraPermissionsManager.java:36`,
  `camera_windows/windows/camera.cpp:10`). New `test/plugin_error_mapping_test.dart` feeds the
  screenshot's exact three-field exception and asserts no output contains `at androidx.`,
  `PlatformException` or `java.util.concurrent`; the wizard widget test asserts the same against the
  rendered tree. The checklist gate carries its own negative test — an adapter declaring nothing must
  report every feature missing — because a gate that cannot fail proves nothing.
  **Not yet verified: on-device behaviour.** The manual passes (Android empty state, Android/Windows
  permission hints, transient `CameraUnavailable` recovery via Refresh) are the user's to run.

  follow-up, since that bullet already owns this work.
