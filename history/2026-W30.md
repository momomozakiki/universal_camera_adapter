### [code] scripts/ezviz_bridge.py, example/lib/tabs/ezviz_tab.dart — working EZVIZ live-view test path via Open Platform + native SDK player
- **What:** Full pivot away from the local-SDK approach (`pyezvizapi`, ports 9010/9020),
  which was conclusively a dead end — the library's decoder doesn't understand this
  camera's "IDMX" local-stream packet container at all, independent of encryption state.
  `scripts/ezviz_bridge.py` rewritten (stdlib-only, `pyezvizapi` dependency dropped
  entirely) around EZVIZ's official Open Platform cloud API: `GET /devices` →
  `device/list`, `GET /config` → `{appKey, accessToken}` from a cached/auto-refreshed
  `token/get`. `example/lib/tabs/ezviz_tab.dart` rewritten to consume this: device list
  → verification-code field + explicit Connect/Reconnect button (keyed
  `ValueKey(serial::code::attempt)` forcing a fresh player instance per tap, avoiding any
  dependency on which button the user taps) → live video via a new small
  `_EzvizNativePlayer` widget.
- **Why:** User wants a reusable, modular Flutter test surface for viewing this camera's
  live feed, for any EZVIZ account/camera, not just this one. HLS/RTMP
  (`live/address/get` protocol=2/3) were tried first and empirically ruled out for this
  account/region (fixed error-placeholder segment; RTMP relay refuses connection) — only
  `ezopen://` (protocol=1) works, and needs EZVIZ's own player logic to resolve, not a
  standard video URL. Evaluated three player approaches in order: embedding EZVIZ's
  EZUIKit JS player in a `webview_flutter` WebView (abandoned — `webview_flutter_windows`
  needs a C++23 compiler this machine's MSVC toolchain doesn't have); the `ezviz_flutter`
  pub package's `EzvizSimplePlayer` convenience widget (added, but had a confirmed logic
  bug — see below); finally `ezviz_flutter`'s lower-level `EzvizPlayer`/
  `EzvizPlayerController` primitives, wrapped in this repo's own thin `_EzvizNativePlayer`.
- **Bugs found and worked around (both in `ezviz_flutter` 1.2.7, not this repo's code):**
  1. `EzvizSimplePlayer._handlePlayerStatus()` marks its internal `_isPlayerInitialized`
     flag `true` as soon as the native SDK reports status `1` ("Init") — which fires
     immediately after the platform view is created, unconditionally — before
     `_initializePlayer()` (the only place that calls `setPlayVerifyCode()`) has ever run.
     `_startLiveStream()` only calls `_initializePlayer()` `if (!_isPlayerInitialized)`,
     so the verification code is silently never applied, for both `autoPlay` and manual
     retry. Confirmed via `adb logcat`: the plugin's own `🔐 Setting verification code`
     debug line never appeared across ~9 real playback attempts on real hardware. Worked
     around by bypassing `EzvizSimplePlayer` entirely.
  2. The native Kotlin side (`EzvizView.kt: onMethodCall`) never calls
     `result.success()`/`result.error()` for `initPlayerByDevice`, `setPlayVerifyCode`, or
     `startRealPlay` (unlike e.g. `openSound`/`capturePicture`, which do) — awaiting these
     calls from Dart hangs forever. `_EzvizNativePlayer` fires them without awaiting;
     actual playback progress/errors are reported via the separate event channel (already
     wired via `setPlayerEventHandler`), not these calls' return values.
- **Verified end-to-end on real hardware:** phone `CPH2113` (Android 12, USB-connected,
  `adb reverse tcp:8765 tcp:8765` to reach the bridge on this laptop). Bridge's
  `/devices`/`/config` confirmed via curl. App rebuilt/reinstalled repeatedly during
  debugging; final build reaches native SDK `startRealPlay` with `setPlayVerifyCode`
  correctly applied (confirmed via the app's own `Applying verification code` debug line
  and sustained ~16fps virtual-display compositing in logcat while connected) and the
  user confirmed live camera connection succeeded. `flutter analyze --fatal-infos` clean
  throughout. Also added: `EzvizTab` bridge-host/verification-code fields persisted via
  `shared_preferences` across app restarts; `example/windows/` scaffolding (via
  `flutter create --platforms=windows .`) so the example app builds on Windows too
  (this EZVIZ tab is Android/iOS-only — `ezviz_flutter` has no Windows implementation,
  same constraint that ruled out `webview_flutter_windows` above).

### [code] example/lib/tabs/ezviz_tab.dart, example/third_party/ezviz_flutter — native per-user EZVIZ login, replacing the bridge
- **What:** Replaced the single-shared-account, laptop-bridge-dependent login flow with EZVIZ's
  own native per-user login: `EzvizAuthManager.openLoginPage()` launches EZVIZ's hosted login
  page (this app never sees a password), `getAccessToken()`/`logout()` manage the resulting
  session, `EzvizDeviceManager.getDeviceList()` replaces the bridge's `/devices` call. New
  `_Step.signIn` step added to `ezviz_tab.dart`; `scripts/ezviz_bridge.py` left in place
  (unreferenced) per explicit instruction, to be deleted once this flow is fully confirmed.
  `ezviz_flutter` is no longer pulled from pub.dev — vendored into
  `example/third_party/ezviz_flutter` (pruned to `lib`/`android`/`ios` only) so four real native
  bugs could be patched directly; `example/pubspec.yaml` now points at it via `path:`, and
  `example/analysis_options.yaml` excludes `third_party/**` from lint (third-party code, not
  ours to restyle).
- **Why:** User's explicit ask: "each user will login at their own account later so it must
  support login feature for each user... the info must be at the phone app with security
  feature." Confirmed via native source (`EzvizManager.kt`) that only the AppKey (public) is
  needed client-side; the AppSecret is never touched by this flow.
- **Bugs found and fixed (all in `ezviz_flutter` 1.2.7 / its native SDK dependency, not this
  repo's original code — each confirmed via `adb logcat` before patching, not guessed):**
  1. `io.github.ezviz-open:ezviz-sdk:5.27`'s AAR ships an empty `AndroidManifest.xml` (zero
     `<activity>` entries) despite compiling in `EzvizWebViewActivity`/`EZAuthHandleActivity` —
     `openLoginPage()` failed with "Unable to find explicit activity class". Fixed by declaring
     both activities in `example/android/app/src/main/AndroidManifest.xml`.
  2. `initSDK`'s native handler called `EZGlobalSDK.getInstance().setAccessToken(accessToken)`
     unconditionally, even when called with `accessToken: ''` — and this tab's own bootstrap
     called `getAccessToken()` *before* `initSDK()` (which throws natively since the SDK
     singleton doesn't exist yet; the Dart wrapper swallows this to `null`), so every cold start
     fell into the "no token" branch and immediately erased the token `initLib()` had just
     silently restored from disk. Every fresh launch required signing in again. Fixed both
     sides: vendored `initSDK` now only calls `setAccessToken` when non-empty; `_bootstrap` now
     calls `initSDK` before `getAccessToken`.
  3. `getDeviceList`'s native mapping sent a nested `cameraInfoList` shape with a raw
     `EZConstants.EZVideoLevel` enum value (e.g. `VIDEO_LEVEL_4K`) — unserializable by Flutter's
     `StandardMessageCodec`, crashing the whole process.
  4. That nested shape was moot anyway: `EzvizDeviceManager.getDeviceList()` actually decodes
     into `ezviz_definition.dart`'s `EzvizDeviceInfo`, a flat model requiring
     `deviceSerial`/`deviceName`/`isSupportPTZ`/`cameraNum` — a completely different, unrelated
     model from the `DeviceInfo`/`CameraInfo` pair in `models.g.dart` that bug 3's fix targeted.
     The real crash was a missing `cameraNum` key, always `null` against a non-nullable `int`
     field ("type 'Null' is not a subtype of type 'int'"). Fixed by rewriting the native mapping
     to the flat shape Dart actually reads.
- **Verified end-to-end on real hardware** (phone `CPH2113`, USB): sign-in → hosted EZVIZ login
  page → device list populated with the signed-in account's own camera → sign-out returns to
  sign-in. Not yet re-verified this session: playback (`_EzvizNativePlayer`, unchanged, expected
  unaffected) and force-quit/relaunch token persistence (expected fixed by bug 2's fix, not
  explicitly re-tested). `flutter analyze --fatal-infos` clean.
- **Deferred (explicit user instruction, unchanged from 2026-07-21):** `scripts/ezviz_bridge.py`
  stays until this flow is fully confirmed, then gets deleted together with rewriting
  `docs/camera/ezviz-integration-notes.md` to describe this architecture as current.

### [feat] lib/src/setup/camera_setup_wizard.dart, example/lib/setup/onvif_setup_wizard.dart, example/lib/{camera_session,tabs/cameras_tab}.dart — edit a saved camera (Epic 2.5 Task 2)

- **What:** A saved camera can now be edited. `CameraSetupWizard` gained an opt-in
  `supportsEditing`/`buildEditor` pair, `OnvifSetupWizard` implements both, `CameraSession` gained

- **Why:** Until now a camera whose IP, port, or password changed could only be deleted and re-added.
  That is not merely tedious: `CameraProfile.id` is minted at save time and is the key the
  `CameraSecretStore` uses, so re-adding strands the old password beyond reach and silently drops
  both the `isDefault` flag and `createdAt`. Editing had to be a distinct entry point, not "run the
  setup flow again".
- **How — the contract (`lib/`):** `supportsEditing` defaults to `false` and the base `buildEditor`
  throws `UnsupportedError`, mirroring how `CameraAdapter.setPan`/`setTilt` default — a backend with
  nothing to edit inherits the default and writes no dead stub (interface segregation). A **third
  invariant** now sits alongside the existing two in the class doc: the profile returned from
  `buildEditor` must preserve `id`, `createdAt` and `isDefault`, built with `copyWith`, never
  `create`.
- **How — ONVIF:** `buildOnvifSetupDraft` takes an optional `existing` profile and switches from
  `CameraProfile.create` to `existing.copyWith(...)`. Keeping this in the **pure helper** rather than
  the form is deliberate: identity preservation is the security-relevant half of editing, and there
  it is testable with no widget, network, or platform channel. `device.id` (`host:port`) *does* change
  when the endpoint is edited — that is the endpoint's identity, not the profile's, and
  `CameraSession`'s onvif matcher keys on `metadata` host/port, so a restore still resolves.
- **Scope, and why it is not wider:** ONVIF gets a full editor; **Rename** is backend-agnostic
  (`displayName` is a plain field on the generic profile) so every camera has it, including builtin
  and EZVIZ. EZVIZ editing (verification code + name) is deliberately **not** written: it cannot be
  exercised on this machine at all, and shipping an unverified credential-editing path is worse than

  existing visibility toggle. The alternative considered was blank-means-unchanged, which never puts
  the secret in a controller. Everything downstream is unchanged — the secret still never reaches the
  persisted profile, is never logged, and never leaves the device.
- **Clearing a password works:** in edit mode the `setSecret` write is unconditional and stores `''`
  when the field is empty. `CameraSecretStore` has no per-key delete, and `CameraSession._withSecret`
  already skips empty secrets, so `''` is the correct representation of "no password now" — without

### [fix] example/lib/tabs/preview_tab.dart, lib/src/camera_adapter.dart, example/test/no_capabilities_adapter_test.dart — bound the preview's height so the whole app stays clickable (Epic 2.5 Task 1 follow-up)

- **Symptom (user-reported, live on Windows):** the app accepted **no** clicks anywhere — not the
  bottom-nav tabs, not the FAB, nothing — once it restored a saved ONVIF camera. Not a tooling
  artifact: the user confirmed they could not click either, and `flutter run` reproduced it on every
  frame.
- **Root cause:** `buildPreview()` carries no sizing guarantee and the two backends differ.
  `FlutterCameraAdapter` returns `CameraPreview`, which self-sizes from its aspect ratio;
  `ONVIFCameraAdapter` returns media_kit's `Video` (`rtsp_preview.dart:98`), which **expands** and
  needs a bounded height. `PreviewTab` places the preview in a `SingleChildScrollView > Column`,
  which offers **unbounded** height. media_kit asserted `BoxConstraints forces an infinite height`
  during layout, the render box was left `size: MISSING`, and from then on **every** hit test in the
  app threw `Cannot hit test a render box that has never been laid out` — killing input on every
  tab, not just Preview.
- **Why it surfaced now — a regression from `08d9ec8` (Task 1), not a new bug:** before Task 1 the
  ONVIF path never reached `buildPreview()`; the `session.isOpen && caps != null` gate hid it behind
  the red screen. Removing that gate was correct, and it exposed a **latent** layout bug that had
  been there all along. Traded a broken tab for a dead app.
- **Fix:** wrap the preview in `AspectRatio(16/9)` in `preview_tab.dart` — bounded for **every**
  backend, names no adapter. `scanner_tab.dart` was already safe (`Expanded` + `StackFit.expand`);
  it was the only other call site and needed nothing.
- **Contract gap closed:** documented on `CameraAdapter.buildPreview()` that sizing is not
  guaranteed and the caller must impose bounded constraints, spelling out both backends' behaviour
  and the app-wide hit-test consequence. This is the same class of gap as Task 1's original crash —
  a backend difference that only the ONVIF path exercised.
- **Why the suite missed it:** every fake `buildPreview()` returned a **self-sizing** widget (the
  `_NoCapabilitiesAdapter` fake used a fixed-size `SizedBox`), which is happy under unbounded height,
  so no test reproduced media_kit's expanding shape. The fake now returns `SizedBox.expand`, and two
  new cases pin the fix: the preview is given a finite non-zero height, and the tab stays
  hit-testable (`ensureVisible` + `tap` on Disconnect, asserting `session.isOpen` flips false). Both
  fail without the `AspectRatio` wrapper.
- **Verified:** live on Windows against the ONVIF camera at `192.168.0.217` — Preview tab streams the
  RTSP feed, tab clicks work, no red screen, restore opened the default "Testing Cam".
  `flutter analyze --fatal-infos` clean at root **and** `example/`; `flutter test` **129 at root**
  and **54 in `example/`** (up from 52 — the two new regression cases).
- **Left unactioned:** the manual edit / rename / kill-relaunch-restore checks (user is driving
  those) and the Android APK build (killed mid-run after filling `C:` to 0 GB — all EZVIZ paths
  remain compile-only, unverified).
