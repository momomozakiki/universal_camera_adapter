## 2026-07-20

### [code] scripts/discover_onvif_cameras.py, scripts/test_rtsp_connection.py — standalone RTSP/ONVIF connectivity diagnostics
- **What:** Two stdlib-only Python diagnostic scripts, outside the `CameraAdapter` contract:
  `discover_onvif_cameras.py` (WS-Discovery UDP multicast probe to `239.255.255.250:3702`,
  parses `ProbeMatch` XAddrs) and `test_rtsp_connection.py` (raw RTSP `OPTIONS`/`DESCRIBE`
  over TCP, Digest RFC 2617 auth with MD5 + `qop=auth` support, Basic fallback, clear
  reachable/auth/stream-found verdict).
- **Why:** User has a real EZVIZ CS-H6c on the LAN and wants to verify network connectivity
  before/independent of the ONVIF backend implementation (Epic 2, still `UnimplementedError`
  scaffolding with no `http`/`xml`/`media_kit` deps declared). Building out the real ONVIF
  backend just to answer "can I reach this camera" would be premature; a small diagnostic
  script answers it now and gives real target params (host/creds/path) for when Epic 2 work
  starts. No `ffmpeg`/`opencv-python` on this machine, so kept dependency-free.
- **Verified:** Ran discovery live against the user's LAN — found and correctly parsed replies
  from two *other* WS-Discovery-capable devices (a Windows WSD endpoint, a network printer)
  after fixing an initial WS-Addressing namespace bug (used 2004/08 instead of the 2005/08
  namespace this network's devices expect) in the probe template. The EZVIZ camera itself did
  not answer WS-Discovery — consistent with the plan's documented risk that ONVIF/discovery
  may be off or unsupported on this model/firmware. Manual IP lookup (EZVIZ app / router DHCP
  list) is the fallback in progress; `test_rtsp_connection.py` is not yet run against the real
  camera pending that IP.

## 2026-07-21

### [code] scripts/ezviz_bridge.py, example/lib/tabs/ezviz_tab.dart — working EZVIZ live-view test path via Open Platform + native SDK player
- **What:** Full pivot away from the local-SDK approach (`pyezvizapi`, ports 9010/9020),
  which was conclusively a dead end — the library's decoder doesn't understand this
  camera's "IDMX" local-stream packet container at all, independent of encryption state.
  `scripts/ezviz_bridge.py` rewritten (stdlib-only, `pyezvizapi` dependency dropped
  entirely) around EZVIZ's official Open Platform cloud API: `GET /devices` →
  `device/list`, `GET /config` → `{appKey, accessToken}` from a cached/auto-refreshed
  `token/get`. `example/lib/tabs/ezviz_tab.dart` rewritten to consume this: device list
  → verification-code field + explicit Connect/Reconnect button (keyed
  `ValueKey(serial::code::attempt)` forcing a fresh player instance per tap, avoiding any
  dependency on which button the user taps) → live video via a new small
  `_EzvizNativePlayer` widget.
- **Why:** User wants a reusable, modular Flutter test surface for viewing this camera's
  live feed, for any EZVIZ account/camera, not just this one. HLS/RTMP
  (`live/address/get` protocol=2/3) were tried first and empirically ruled out for this
  account/region (fixed error-placeholder segment; RTMP relay refuses connection) — only
  `ezopen://` (protocol=1) works, and needs EZVIZ's own player logic to resolve, not a
  standard video URL. Evaluated three player approaches in order: embedding EZVIZ's
  EZUIKit JS player in a `webview_flutter` WebView (abandoned — `webview_flutter_windows`
  needs a C++23 compiler this machine's MSVC toolchain doesn't have); the `ezviz_flutter`
  pub package's `EzvizSimplePlayer` convenience widget (added, but had a confirmed logic
  bug — see below); finally `ezviz_flutter`'s lower-level `EzvizPlayer`/
  `EzvizPlayerController` primitives, wrapped in this repo's own thin `_EzvizNativePlayer`.
- **Bugs found and worked around (both in `ezviz_flutter` 1.2.7, not this repo's code):**
  1. `EzvizSimplePlayer._handlePlayerStatus()` marks its internal `_isPlayerInitialized`
     flag `true` as soon as the native SDK reports status `1` ("Init") — which fires
     immediately after the platform view is created, unconditionally — before
     `_initializePlayer()` (the only place that calls `setPlayVerifyCode()`) has ever run.
     `_startLiveStream()` only calls `_initializePlayer()` `if (!_isPlayerInitialized)`,
     so the verification code is silently never applied, for both `autoPlay` and manual
     retry. Confirmed via `adb logcat`: the plugin's own `🔐 Setting verification code`
     debug line never appeared across ~9 real playback attempts on real hardware. Worked
     around by bypassing `EzvizSimplePlayer` entirely.
  2. The native Kotlin side (`EzvizView.kt: onMethodCall`) never calls
     `result.success()`/`result.error()` for `initPlayerByDevice`, `setPlayVerifyCode`, or
     `startRealPlay` (unlike e.g. `openSound`/`capturePicture`, which do) — awaiting these
     calls from Dart hangs forever. `_EzvizNativePlayer` fires them without awaiting;
     actual playback progress/errors are reported via the separate event channel (already
     wired via `setPlayerEventHandler`), not these calls' return values.
- **Verified end-to-end on real hardware:** phone `CPH2113` (Android 12, USB-connected,
  `adb reverse tcp:8765 tcp:8765` to reach the bridge on this laptop). Bridge's
  `/devices`/`/config` confirmed via curl. App rebuilt/reinstalled repeatedly during
  debugging; final build reaches native SDK `startRealPlay` with `setPlayVerifyCode`
  correctly applied (confirmed via the app's own `Applying verification code` debug line
  and sustained ~16fps virtual-display compositing in logcat while connected) and the
  user confirmed live camera connection succeeded. `flutter analyze --fatal-infos` clean
  throughout. Also added: `EzvizTab` bridge-host/verification-code fields persisted via
  `shared_preferences` across app restarts; `example/windows/` scaffolding (via
  `flutter create --platforms=windows .`) so the example app builds on Windows too
  (this EZVIZ tab is Android/iOS-only — `ezviz_flutter` has no Windows implementation,
  same constraint that ruled out `webview_flutter_windows` above).
